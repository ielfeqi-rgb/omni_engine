# Security Policy

At **Omni Engine**, security, determinism, and data sovereignty are primary architectural invariants. Because Omni Engine compiles, sandboxes, and executes code generated by autonomous AI agents, we enforce rigorous security standards across all layers of the stack.

---

## 1. Supported Versions

We provide active security patches and vulnerability remediation for the following release lines:

| Version | Supported | Status |
| :--- | :---: | :--- |
| **`v2.2.x`** | :white_check_mark: | **Active Production Line (Frozen Baseline)** |
| `v2.1.x` | :x: | End of Life (Deprecated) |
| `< v2.1.0` | :x: | End of Life (Deprecated) |

We strongly recommend all users and organizations maintain deployment on the latest patch of `v2.2.x`.

---

## 2. Reporting a Vulnerability

**DO NOT report suspected security vulnerabilities through public GitHub issues or public discussions.**

If you discover a security vulnerability or potential attack vector in Omni Engine, please disclose it responsibly:

- **Primary Security Contact:** Ibrahim El Feqi
- **Email:** [ielfeqi@gmail.com](mailto:ielfeqi@gmail.com)
- **Subject Line:** `[SECURITY] Omni Engine Vulnerability Report - <Brief Component Description>`

### Information to Include in Your Report
To accelerate investigation and remediation, please provide:
1. **Component Affected:** (e.g., Bubblewrap cleanroom jail, `MemoryVfs` path resolution, C-FFI inference boundary, API authentication).
2. **Severity Assessment:** Impact on host filesystem integrity, memory corruption, privilege escalation, or host container escape.
3. **Reproducible Proof of Concept (PoC):** Step-by-step commands, minimal GGUF model scenario, or JSON blueprint triggering the vulnerability.
4. **Environment Details:** Linux distribution, kernel version, CPU architecture, and whether `--allow-unsandboxed` was active.

---

## 3. Response Process & SLA

Upon receiving a private security report:
1. **Acknowledgment:** We will acknowledge receipt of your report within **48 hours**.
2. **Assessment:** Our core systems team will verify and triage the finding within **5 business days**.
3. **Patch & Release:** A patch will be authored, tested against the 150-test invariant suite, and published in an expedited patch release (`v2.2.x`).
4. **Public Advisory:** We will publish a GitHub Security Advisory crediting the finder (if desired) after a patch is deployed.

---

## 4. Architectural Security Commitments

Omni Engine is built around fail-closed security guarantees:
- **Zero-Cloud Isolation:** The engine makes zero unsolicited outbound network calls. All inference and synthesis occur 100% on-device in local RAM.
- **Fail-Closed Cleanroom:** Untrusted operations run inside unprivileged Linux user namespace containers (`bwrap`) with read-only root filesystems and restricted temporary directories.
- **VFS Boundary Clamping:** Workers cannot write or read files outside their declared `read_set` and `write_set` boundaries (`VfsBoundaryError`).
- **Zero-Wipe Invariant:** Verified existing codebase structures are frozen, mathematically preventing accidental or malicious code deletion during modification passes.
